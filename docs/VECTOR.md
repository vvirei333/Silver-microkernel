# Вектор: консоль + окно браузера на хосте + Linux ABI

Этот документ фиксирует направление после удаления графической подсистемы
(2026-11-08) и отвечает на вопрос «как совместить консоль, браузер в отдельном
окне и Linux-слой».

## 1. Что реально нужно

1. **Планшет**: WerewolfOS в консоли, все утилиты, сеть.
2. **Браузер**: отдельное окно, рисуется на хосте (Qt и т.п.).
3. **В перспективе**: Linux ABI, чтобы попробовать мобильную оболочку Phosh.

Это три независимых слоя. Их нельзя делать одним куском.

## 2. Браузер: где живёт рендер

Есть два честных варианта.

### A. Гость рисует, хост показывает окно (рекомендую)

- Гость: HTTP-клиент + разбор HTML + раскладка в общий RGBA-буфер.
- Хост: Qt-окно, которое близко к `memcpy` блитит этот буфер и шлёт обратно
  мышь/клавиатуру.
- В госте **нет композитора**: один surface на окно, damage-прямоугольники.
- Плюсы: всё «наше», контролируемо, минимальный host-код; окно — просто
  телеметрия поверхности.
- Минусы: «рабочий браузер» = только тот HTML/CSS-подмножество, которое мы
  сами реализуем. HTTPS/TLS — отдельная большая задача (либо host-proxy).

### B. Хост рендерит настоящим движком (QtWebEngine/WebKit)

- Гость отдаёт только сеть/ОС-сервисы, окно и движок — на хосте.
- Плюсы: настоящий web уже завтра.
- Минусы: это уже не браузер WerewolfOS, а host-приложение; зависимость от
  QtWebEngine и хоста. Для «операционной системы» это компромисс.

**Рекомендация:** начать с A (свой минимальный браузер, host-окно), а B держать
как быстрый демо-путь. Для HTTPS на первом этапе — host-proxy: хост забирает
URL по TLS и отдаёт документ в гостя; позже можно свой TLS-стек.

## 3. Протокол окна (host ↔ guest)

Не воскрешать композитор. Минимальный контракт:

```
shared memory (ivshmem на QEMU / файл на хосте):
  header: magic, width, height, stride, format, frame_seq, damage_count
  damage[8]: x, y, w, h
  pixels:   RGBA8888, stride * height
  input ring: type, x, y, buttons, key, wheel
```

- Гость: `window_server` владеет буфером и публикует `frame_seq`.
- Хост: Qt-приложение (`tools/window-viewer`) маппит ту же память, блитит при
  смене `frame_seq`, пишет ввод в ring.
- На QEMU: `-device ivshmem-plain,memdev=...` + `memory-backend-file`.
- На реальном планшете ivshmem нет; там либо локальный текстовый/графический
  вывод, либо стриминг окна по сети/USB (позже).

## 4. Linux ABI: что реально, а что нет

### Реально в обозримом будущем

- **Personality-слой в ядре**: у задачи флаг `Abi::Linux`; на `svc` ядро
  разбирает Linux-номер syscall (x8) и транслирует в VFS/память/IPC.
- Подмножество: `read/write/openat/close/lseek/fstat/mmap/munmap/brk/exit/
  exit_group/clock_gettime/getpid/getuid/getrandom/ioctl(TTY)/poll`.
- Цель: **статические musl-бинарники** — `hello`, отдельные applets busybox
  (`ls`, `cat`, `echo`, `wc`), затем `sh`.
- Это даёт «Linux-совместимую консоль» без графики и без Phosh.

### Не реально «просто подружить»

Phosh — это не syscall-слой, а весь GNOME-стек: Wayland (phoc), GTK, GLib,
D-Bus, systemd/logind, udev, EGL/GLES, input, NetworkManager, PulseAudio.
Чтобы он завёлся, нужны:

1. Linux ABI с потоками (`clone`), `futex`, сигналами, `/proc`, `/sys`, `ioctl`;
2. динамический линкер и glibc/musl-совместимость;
3. Wayland-композитор и GPU/DRM (или мост в host);
4. D-Bus и системные сервисы.

Это отдельный multi-year трек. Начинать с Phosh — почти гарантированный
тупик. Начинать с консольных Linux-бинарников — нормальный, проверяемый путь.

**Вывод:** Linux ABI — да, как консольный personality-слой. Phosh — только
после того, как этот слой научится запускать busybox/sh, и только если проект
сознательно выберет Linux-совместимый userland. Иначе дешевле сделать свой
минимальный UI/браузер.

## 5. Планшет: чем выводить консоль

У планшета (SM8650) нет доступного UART; после удаления графики у него нет и
вывода. Для консольной ОС нужен **текстовый framebuffer-консоль** (8×8 шрифт,
скролл, курсор) — это не композитор и не «графика», а ~200 строк. Без него
планшет слепой.

- QEMU/десктоп: serial + host-окно Qt.
- Планшет: минимальный текстовый framebuffer + (позже) host-стриминг окна.

## 6. Этапы

| Этап | Результат | Оценка |
| --- | --- | --- |
| A | Консоль + утилиты + сеть (DHCP/DNS/TCP/`wget`) | недели |
| B | Текстовый framebuffer-консоль на планшете | дни-неделя |
| C | Host-окно: ivshmem + Qt-viewer, протокол damage/input | 1–2 недели |
| D | Свой минимальный браузер (HTTP + HTML-подмножество) в окне | месяцы |
| E | Linux ABI для статических musl-бинарников (консоль) | месяцы |
| F | Оценка Phosh/Wayland (go/no-go) | после E |

## 7. Открытые вопросы

1. Браузер: свой рендер (A) или QtWebEngine на хосте (B)? Рекомендация — A.
2. HTTPS: host-proxy на первом этапе или свой TLS позже?
3. Планшет: текстовый framebuffer сейчас или сначала только QEMU?
4. Linux ABI: цель — busybox/sh (реально) или сразу Phosh (нереально сейчас)?
5. Окно на планшете: локальный вывод или стриминг на хост по сети/USB?
